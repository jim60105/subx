## 1. Spike: confirm the toolchain before writing anything

- [x] 1.1 Determine the mutually compatible versions of `specta`, `tauri-specta` and `specta-typescript` for `tauri` 2.11.5, working from the crates' own current documentation rather than from this change's prose — the RC's builder API has moved between releases. Record the working versions and the actual API shape in the change notes. **Result:** `specta =2.0.0-rc.25` (feature `derive`), `specta-typescript =0.0.12`, `tauri-specta =2.0.0-rc.25` (features `derive`, `typescript`) resolve cleanly against `tauri` 2.11.5. API: `Builder::<R>::new().commands(collect_commands![…]).events(collect_events![…])`, with `builder.invoke_handler()`, `builder.mount_events(app)` and `builder.export(Typescript::default(), path)`. `Builder` is generic over the runtime, so one function serves both `Wry` and `MockRuntime`. Full findings in design.md D8
- [x] 1.2 Build a throwaway proof covering the three things that could invalidate the plan, not just the happy path: (a) derive `Type` on one DTO, collect one command, emit TypeScript, and confirm one `Builder` can supply **both** the invoke handler and the export — if it cannot, the "same source as the handler registration" requirement is unsatisfiable as written; (b) include a DTO field carrying `#[serde(skip_serializing_if = "Option::is_none")]` (use `ErrorDto::hint_code` or `ConnectionTestResult::latency_ms`) and record whether the output is `field?: T` or `field: T | null` — these are different wire contracts and the answer decides task 3.3; (c) compile an empty event collection, to confirm the "events wired before they exist" pattern actually works. **If no compatible combination exists, stop here and report it** — the fallback is `ts-rs` with reduced scope (types only, commands still hand-named), which is a different change, not a workaround to improvise. **Result:** (a) confirmed — one builder supplies both, and `Builder.invoke_handler()` takes `&self`; (b) neither form was available as assumed: unified mode *rejects* `skip_serializing_if` outright (`unified mode cannot represent conditional omission`) and phased mode expresses it only by splitting every affected DTO into a `_Serialize`/`_Deserialize` pair, so the attribute was dropped and the wire now carries explicit nulls; (c) confirmed — an empty `collect_events![]` compiles and generates no event section, and a fixture event proves declaring one is sufficient. A fourth finding not anticipated by the plan: specta refuses to export `u64`, which forced `latency_ms` to `u32`
- [x] 1.3 Pin the confirmed versions as exact requirements (`=2.0.0-rc.25` style, not caret ranges) in `src-tauri/Cargo.toml`, so an RC bump is always a deliberate act with its own diff

## 3. Frontend: cut over to the generated contract

- [x] 3.1 Generate `src/types/bindings.ts` and commit it
- [x] 3.2 Reduce `src/types/ipc.ts` to re-exports of the generated types plus the hand-written `isErrorDto` guard, defined against the generated `ErrorDto`; the eight existing import sites must keep working unchanged
- [x] 3.3 **Diff the generated declarations against the hand-written ones they replace and record the comparison.** Classify every discrepancy before reconciling it: a field that simply disagrees is a pre-existing transcription bug and must be reported; a difference in how optionality is expressed (`latencyMs?: number` versus `latencyMs: number | null` — see 1.2b) is the tool describing a different wire shape, and is fixed by making the type and the wire agree, either with a specta optional-key attribute or by dropping `skip_serializing_if`. Neither kind may be silently absorbed. **Result:** two discrepancies, both classified and reconciled rather than absorbed. (i) `latencyMs?: number` was a transcription bug — the Rust was `Option<u64>`, a range JavaScript's f64 numbers cannot represent, and specta refuses to emit it; narrowed to `u32`. (ii) All three optional fields changed from optional-key to `T | null`, the optionality case: the type and the wire now agree, and `error.rs`'s serialization test was inverted to pin the new shape. Every other field corresponded one-to-one
- [x] 3.4 Rewrite `settingsApi.ts`'s three function bodies to call the generated bindings instead of `invoke<T>("…")`, keeping `AI_FIELDS`, `CONFIG_KEYS`, `AI_PROVIDERS` and their comments — those encode product decisions the backend does not know about

## 6. Traceability and follow-on

- [x] 6.1 Sync this change's `typed-ipc` and `verification-gates` deltas into `openspec/specs/` so the traceability gate sees the new scenarios, following the same pattern `add-verification-gates` established — then **verify the sync-then-archive round trip is idempotent** (archiving must not double-apply an already-synced ADDED or MODIFIED requirement). If it is not, both this change and `add-verification-gates` need the same remedy; report it rather than working around it locally. **Result: safe, with a caveat worth knowing.** Tested on a throwaway copy of `openspec/`. The `openspec archive` CLI does try to apply the deltas, detects the already-applied requirement, and *aborts without writing anything* (`ADDED failed for header … - already exists. Aborted. No files were changed.`) — so nothing is ever double-applied or corrupted, but the plain CLI path is blocked after a manual sync. `openspec archive --skip-specs` completes cleanly and leaves the requirement counts unchanged, as does the archive skill's own `mv`-based procedure, which is what `add-verification-gates` used. No remedy needed for either change; use `--skip-specs` (or the skill) when archiving after a mid-implementation sync
