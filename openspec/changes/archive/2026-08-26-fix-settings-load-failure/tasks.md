## 2. GUI — settings form stays editable on load failure

- [x] 2.1 In `src/features/settings/useSettingsForm.ts`, any strict `getConfig()` rejection while `config` is still null (initial load or a focus refetch) triggers the shared tolerant fallback: call `getConfigTolerant()`; on success use its result as the working `config` (draft from it) and keep `loadError` set; on failure fall back to a `DEFAULT_CONFIG` constant mirroring the crate's `Config::default().ai` (provider `openai`, model `gpt-4.1-mini`, base URL `https://api.openai.com/v1`, no key). Gate the focus refetch while the initial bootstrap is in flight (`bootstrappingRef`) so it cannot orphan the in-flight tolerant call; mirror the latest config in a `configRef` for the fallback trigger check.
- [x] 2.2 Update `src/features/settings/SettingsScreen.tsx` so the AI form renders whenever `config` is non-null (including the tolerant result or the fallback), the `loadError` `ErrorNotice` renders above the form as a non-blocking banner, and the loading placeholder shows only while `config === null && loadError === undefined`.
- [x] 2.3 Update `persist()` in `useSettingsForm.ts` with the revised save-error rules: `saveError` denotes a non-field action error (per-field failures stay in `fieldErrors`); clear any previous `saveError` immediately after the write loop when every field write succeeded; when all writes succeeded but the strict re-fetch failed, refresh `config` through `getConfigTolerant()` (same draft keep-rule, so the saved API key field resets to its masked placeholder); when some write failed, a failed re-fetch sets `saveError`.
